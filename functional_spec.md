# Функциональные требования к боту расписания v2

## Назначение и общая концепция

Telegram-бот предназначен для автоматизированного предоставления школьного расписания, отслеживания замен и управления внеурочной активностью. Основная концепция версии v2 — отказ от жесткого кодирования (хардкода) классов в пользу динамической модульной архитектуры, работающей с полным дампом расписания школы. Система поддерживает мультипользование, семейные аккаунты и индивидуальные настройки нотификаций

## 1. Роли и семейная модель

### 1.1. Поддерживаемые роли

Бот должен поддерживать следующие роли пользователей:

- **Ребёнок (child)** — ученик школы, получает своё расписание и уведомления. Базовый пользователь. При регистрации указывает имя, класс, группу и подгруппу.
- **Родитель (parent)** — один или несколько родителей/опекунов ребёнка; создатель или участник семьи. Управляет профилями детей, добавляет/удаляет пользователей внутри семьи, настраивает дополнительные занятия.
- **Учитель (teacher)** — преподаватель школы, просмотр преподавательского расписания и сетки занятости по кабинетам.
- **Наблюдатель (observer)** — например, бабушка/дедушка; имеет права только на просмотр расписания, без управления профилями.[file:79][web:88]
- **Администратор (admin)** - системная роль (назначается через config.py), имеющая доступ к статистике, управлению пользователями и принудительному обновлению кэша.

### 1.2. Семейная модель
- Родитель, создавший семью, получает флаг is_family_admin.
- Каждый ребёнок привязан к записи **семьи** (`families`), у которой есть уникальный `family_code`.
- Родители и наблюдатели подключаются к семье по коду (`/link_family`), после чего получают доступ ко всем детям в этой семье.[file:79]
- Родитель или наблюдатель может просматривать расписание даже если ни один ребенок не добавлен, выбрав класс и группу по аналогии с учеником(сохранение последнего выбора, сброс через настройки профиля)
- Один родитель может быть привязан к нескольким детям (например, дети из разных классов).
- Один ребёнок может иметь нескольких родителей/наблюдателей.[web:88][web:93]

- Родительский контроль: Родитель имеет право заблокировать изменение настроек уведомлений для профиля ребенка (флаг parent_control_notifications в БД). Ребенок не сможет выключить утренние будильники.
- Мультипрофильность: Родитель может выбрать от 1 до 3 детей в меню для параллельного отслеживания. Клавиатура расписания должна иметь переключатель [👦 Иван 5А] [👧 Анна 8Б].

### 1.3. Управление пользователями в семье

- Создатель семьи (первый родитель) имеет права на управление участниками:
  - просмотр списка детей и взрослых;
  - удаление участников (например, если кто‑то вышел из семьи или неправомерно присоединился);
  - при необходимости блокировка уведомлений для конкретного взрослого.
- Ребёнок при регистрации выбирает:
  - отображаемое имя (для удобства родителей);
  - `class_id` (класс по справочнику NIKA); ## учесть что ребенок class_id не знает. Он знает только свою цифру и букву например 5А, поэтому чтобы не ошибиться с написанием проще парсить ему весь список или жестко ограничить ввод чтобы не было ошибок ввода
  - `group_id` (группа по NIKA, например «Группа 1», «Девочки»); учесть что ребенок group_id не знает. Он знает только свою цифру группы, поэтому чтобы не ошибиться с написанием проще парсить ему весь доступный список в его классе или жестко ограничить ввод чтобы не было ошибок ввода
  - при необходимости подгруппу/доп. характеристику (из `CLASSGROUPS`).[file:79]

## 2. Регистрация и настройка уведомлений

### 2.1. Регистрация и выбор роли

- Команда `/start`:
  - предлагает выбрать роль (ребёнок, родитель, учитель, наблюдатель);
  - при выборе «Родитель» или «Наблюдатель» — запрос кода семьи (`family_code`);
  - при выборе «Ребёнок» — форма выбора класса, группы, имени.[file:79]
- Профиль пользователя (`users`) хранит:
  - роль;
  - `class_id`, `group_id` (для ребёнка);
  - `teacher_id` (для учителя);
  - `family_id` (для членов семьи);
  - настройки уведомлений: `pre_lesson_offset_minutes`, `changes_window_days`.[file:79]

### 2.2. Управление уведомлениями

- Каждый пользователь может:
  - полностью отключить уведомления;
  - настроить:
    - `pre_lesson_offset_minutes` — за сколько минут до урока приходят предурочные уведомления;
    - `changes_window_days` — окно дней для уведомлений об изменениях расписания (по умолчанию 3).[file:79]
- **Опционально (политика школы):** родитель может «заблокировать» настройки уведомлений ребёнка:
  - запрет изменения времени предурочных уведомлений ребёнком;
  - запрет отключения уведомлений ребёнком.  
  Это отдельный флаг в профиле ребёнка, доступный только роли «parent».[web:88]

## 3. Работа с несколькими детьми

- Родитель может привязать к своему профилю до 1–3 (или больше) детей внутри семьи.
- В боте реализуется выбор активного ребёнка:
  - списком детей с именем и классом;
  - переключение «фокусного» ребёнка для команд `/today`, `/week` и просмотра изменений.
- Для каждого ребёнка родитель может включать/выключать уведомления отдельно (например, не слать предурочные для старших детей).[web:88][web:92]

## 4. Уведомления

### 4.1. Уведомления об изменении расписания

- Изоляция часовых поясов: Все расчеты времени и триггеры APScheduler используют строго заданный ZoneInfo (например, "Asia/Novosibirsk"), использование naive datetime запрещено.
- Бот отслеживает изменения расписания через мёрж `CLASS_SCHEDULE`/`CLASS_EXCHANGE` и `TEACH_SCHEDULE`/`TEACH_EXCHANGE`.[file:79]
- Для записей с `is_exchange = 1` или `is_cancelled = 1` в `schedule_cache`:
  - уведомления отправляются только если дата урока попадает в окно `[today, today + changes_window_days]`;
  - поле `is_change_notified` предотвращает дубли — уведомление отправляется один раз.[file:79]
- Ежедневный брифинг: Утренняя рассылка свежего расписания (с учетом доп. занятий). Отключаемая функция с настраиваемым таймингом. Пользователь может настроить глубину окна:
  - по умолчанию `changes_window_days = 3`;
  - родители могут увеличить или уменьшить этот интервал в разумных пределах.
- Предурочные оповещения: Напоминания за N часов/минут до начала первого урока. Реализуется через интервальный планировщик (запуск каждые 5 минут), вычисляющий delta = start_time - now. Значение сдвига хранится в колонке pre_lesson_offset_minutes

### 4.2. Ежедневные утренние уведомления

- Ежедневно, за `N` часов до первого урока ребёнка, бот отправляет сводку расписания на день:
  - список уроков по данным NIKA;
  - дополнительные занятия (`extra_classes`), введённые вручную.[file:79]
- Время отправки рассчитывается по таймзоне `TIMEZONE` (например, `Asia/Novosibirsk`) и расписанию звонков (`LESSON_TIMES`).[file:79][web:85]
- Уведомления можно:
  - полностью выключить;
  - настроить `N` (через `pre_lesson_offset_minutes` и комбинацию с временем первого урока).

### 4.3. Предурочные уведомления (за N минут до урока)

- Каждые 5 минут APScheduler запускает `send_pre_lesson_reminders`:
  - выбирает уроки на текущую дату (`is_cancelled = 0`);
  - считает дельту `delta = start_time - now` в минутах;
  - присылает уведомление, если `0 < delta <= pre_lesson_offset_minutes` и `is_notified = 0`.[file:79][web:73]
- После отправки:
  - в `schedule_cache` `is_notified` устанавливается в `1`, чтобы исключить дубли.

## 5. Дополнительные занятия (кружки, секции)

- Родитель может добавлять для ребёнка доп. занятия:
  - день недели;
  - время начала/конца;
  - описание (название кружка);
  - место (кабинет/секции).[file:79]
- Доп. занятия:
  - хранятся в таблице `extra_classes`;
  - отображаются в расписании ребёнка как отдельные элементы (с меткой «Доп. занятие»);
  - учитываются в утренних и предурочных уведомлениях.
- Предусмотрен полный CRUD-цикл:
  - добавление;
  - удаление;
  - изменение времени/описания.
- Строгая валидация ввода времени через datetime.strptime для защиты базы данных.

## 6. Просмотр расписания

### 6.1. По ребёнку/классу

- Команды типа `/today`, `/3days`, `/week` позволяют:
  - показать расписание на:
    - один день;
    - следующие 3 дня;
    - текущую неделю;
    - следующую неделю.[file:79]
- Расписание формируется из `schedule_cache` + `extra_classes`:
  - учитываются группы (`group_id`) и замены;
  - для ребёнка фильтруется по его `group_id` или `"ALL"`.

### 6.2. История изменений расписания

- Бот предоставляет краткую сводку изменений:
  - добавленные/удалённые уроки;
  - замены предметов/кабинетов;
  - отмены (`is_cancelled = 1`).[file:79]
- История может быть реализована:
  - либо по данным `schedule_cache` (по флагам и датам создания/обновления);
  - либо через отдельную таблицу `change_history`.
- Пользователь, не включивший уведомления по изменениям, может вручную запросить эту сводку за последние N дней.

### 6.3. Расписание учителя

- Учитель (роль `teacher`) может запросить:
  - расписание на сегодня;
  - расписание на неделю.[file:79]
- Для этого используются данные `TEACH_SCHEDULE`/`TEACH_EXCHANGE`:
  - выводятся классы, кабинеты, предметы;
  - отдельно учитываются методические занятия.

## 7. Админ‑функционал

- В конфиге задаётся роль **admin** (список Telegram user_id или специальный флаг в БД).
- Админ может:
  - просматривать список всех пользователей и их роли;
  - видеть, к каким семьям/классам они привязаны;
  - управлять профилями (в крайних случаях удалять пользователей или семьи);
  - включать/выключать глобальные функции (например, временно отключить уведомления для всех).[web:92]

## 8. Защита от переполнения БД и управление неактивными пользователями
- Сборка мусора (Garbage Collection) кэша: В методе refresh_from_remote реализовано автоматическое удаление дампов raw_nika_cache старше 7 дней для защиты БД от переполнения
- В таблице `users` хранится `last_active_at` (дата последней активной команды/взаимодействия).
- Создается фоновая задача (cron), которая раз в сутки проверяет базу. Если пользователь не взаимодействовал с ботом более 60 дней, система автоматически переводит is_notifications_enabled в False, снижая нагрузку на CPU и Telegram API. При отправке команды /start подписка возобновляется.
- Фоновый мониторинг должен:
  - обнаруживать пользователей, неактивных более N дней;
  - для них:
    - отключать уведомления (чтобы не слать лишние сообщения);
    - по настройке — через M дней дополнительно очищать связанные кэш‑записи (например, старые `schedule_cache` и `raw_nika_cache`), сохраняя при этом семейные связи для защиты БД от переполнения.  
- Важно не удалять данные молча; возможно, достаточно «soft deactivate»:
  - ставить флаг `is_active = 0`;
  - переставать слать уведомления до следующего взаимодействия пользователя.

- Панель Администратора: Добавлен скрытый модуль handlers/admin.py (доступ по списку ID из config.py). Включает команды /stats (количество живых юзеров, семей, распределение по ролям) и /broadcast (рассылка технических уведомлений, например, о падении сайта школы).
- Резервирование данных: Бот автоматически использует данные из schedule_cache в случае недоступности [https://lyceum.nstu.ru](https://lyceum.nstu.ru), логируя ошибку и уведомляя администратора. Работоспособность бота не зависит от аптайма школьного сервера.  

## 9. Источник данных и алгоритм парсинга
- Сбор данных: Бот загружает JS-файл nika_data_*.js со страницы [https://lyceum.nstu.ru/rasp/schedule.html](https://lyceum.nstu.ru/rasp/schedule.html).
- Нормализация: Парсер извлекает JSON-объект var NIKA = {...}. Модуль NikaNormalizer мапит идентификаторы из CLASS_SCHEDULE и TEACH_SCHEDULE со справочниками CLASSES, TEACHERS, ROOMS, SUBJECTS. 
- Сетка звонков: Время начала (start_time) и окончания (end_time) уроков берется динамически из массива LESSON_TIMES по индексу номера урока.  
- Обработка аномалий: Пустые строки ("") в данных системы заменяются на None. При отмене урока (флаг "F") массивы учителей и кабинетов игнорируются, чтобы избежать KeyError. Уроки для всего класса мапятся с маркером "ALL" для безопасного сохранения в БД.

## 9.1. Архитектура и База Данных (aiosqlite)
Система использует плоскую денормализованную структуру кэша расписания для высокой производительности.  
Ключевые таблицы:
- users: Хранит user_id, role, family_id, class_id, group_id, teacher_id. Дополняется полями: last_active_at (дата последней активности), parent_control_notifications (булево), is_notifications_enabled (булево).  
- families: Хранит family_code и admin_user_id (создатель семьи).  
- extra_classes: Хранит доп. занятия с привязкой к family_id или user_id.  
- schedule_cache: Денормализованное расписание. Первичный ключ id формируется как period_id + class_id + date + lesson_num + group_id. Используется логика INSERT OR REPLACE (UPSERT) для обновления данных без дублей.  
- change_history: Журнал аудита замен и отмен.  
- raw_nika_cache: Таблица для кратковременного хранения сырых JS-дампов для дебага.  


## 10. Принцип рефакторинга существующего проекта

- Бот должен сохранить основные UX‑принципы и команды существующей версии:
  - форматы вывода расписания;
  - базовые команды `/today`, `/week`, `/set_class` и т.п.[file:79]
- Реализация переносится:
  - с старого HTML‑парсинга на новый движок парсинга NIKA (JS);
  - с моноклассной логики (`CLASS_ID = "016"`) на универсальное ядро школы.[file:27][file:79]
- Логика бота должна использовать новые сервисы:
  - `ScheduleServiceV2`;
  - `ProfileService`;
  - `NotificationService`;
  - а не напрямую работать с `NIKA`.
