# Техническое задание на разработку Telegram-бота школьного расписания v2

## 1. Назначение и общая концепция

Telegram-бот предназначен для автоматизированного предоставления школьного расписания, отслеживания замен и управления внеурочной активностью (кружки, секции), с поддержкой мультипользования (семьи, учителя, наблюдатели).[file:79]

Версия v2 строится на следующих принципах:

- **Отказ от хардкода классов**: никакие классы (например, `"016"` для 6А) не зашиваются в коде; вся информация берётся из дампа NIKA (`CLASSES`, `CLASS_SCHEDULE`, `TEACH_SCHEDULE`).[file:27][file:79]
- **Модульная архитектура**: отдельные слои для парсинга NIKA, доменной модели школы, репозитория расписания, сервисов (ScheduleServiceV2, ProfileService, NotificationService) и слоя бота с обработчиками команд.[file:79]
- **Семейная модель и ролевой доступ**: учёт ролей ребёнка, родителя, учителя, наблюдателя и администратора, привязка пользователей к семьям по `family_code` и управление профилями.[file:79]
- **Гибкая система уведомлений**: индивидуальные настройки предурочных уведомлений и окна по изменениям расписания, с защитой от спама и дублей.[file:79]
- **Отказоустойчивость**: денормализованное расписание в SQLite (aiosqlite), краткосрочный сырой кэш NIKA, работа бота из локального кэша при недоступности сайта школы.[file:79]

Бот создаётся как рефакторинг существующего проекта: UX и основные команды сохраняются, но весь парсинг и доступ к данным переводятся на новый движок JS/NIKA и модульную архитектуру.[file:27][file:79]


## 2. Ролевая модель и семейная структура

### 2.1. Роли пользователей

Поддерживаются следующие роли:

- **parent (Родитель)** — создатель или участник семьи. Управляет профилями детей, настраивает дополнительные занятия, может управлять уведомлениями ребёнка.[file:79]
- **child (Ребёнок)** — базовый пользователь. При регистрации указывает отображаемое имя, класс (`class_id`), группу (`group_id`) и, при необходимости, подгруппу по `CLASSGROUPS`.[file:79]
- **observer (Наблюдатель/бабушка)** — имеет доступ только к просмотру расписания, без прав на редактирование профилей и дополнительных занятий.[file:79]
- **teacher (Учитель)** — может просматривать расписание преподавателя (по `TEACH_SCHEDULE`) и сетку занятости по кабинетам.[file:79]
- **admin (Администратор)** — системная роль (по списку user_id в `config.py` или флагу `is_admin` в БД); имеет доступ к статистике, управлению пользователями, семьям и принудительному обновлению кэша.[file:79]

### 2.2. Семейная модель

- Семья представлена таблицей `families` с полями `id` и `family_code`.
- Родитель создаёт семью и получает флаг `is_family_admin` (например, по полю `admin_user_id` в `families`).[file:79]
- Другие родители и наблюдатели подключаются к семье по команде `/link_family` и вводу `family_code`.
- Один родитель может быть привязан к нескольким детям (мультипрофильность): в интерфейсе предусмотрен выбор активного ребёнка, например клавиатурой `[👦 Иван 5А] [👧 Анна 8Б]`.[web:82][web:88]
- Один ребёнок может иметь нескольких родителей/наблюдателей.

### 2.3. Управление участниками семьи

- Создатель семьи (или админ) может:
  - просматривать список участников (дети, родители, наблюдатели);
  - удалять участников семьи (например, при выходе из семьи или ошибочном подключении);
  - при необходимости блокировать уведомления для конкретного взрослого.

- Ребёнок при регистрации должен выбрать:
  - имя (логическое имя для отображения родителям);
  - класс (`class_id` из `CLASSES`);
  - группу (`group_id` из `CLASSGROUPS`, при наличии деления);
  - при необходимости подгруппу/специализацию (дополнительные значения `CLASSGROUPS`).[file:79]

### 2.4. Родительский контроль уведомлений

- В таблице `users` предусмотрено поле `parent_control_notifications INTEGER NOT NULL DEFAULT 0`.
- Если `parent_control_notifications = 1` для ребёнка, он не может:
  - выключать утренние уведомления;
  - менять `pre_lesson_offset_minutes` и `changes_window_days`.
- В этом случае NotificationService использует настройки, заданные родителем или семейные настройки.


## 3. Источник данных и парсинг NIKA

### 3.1. Источник данных

- Страница расписания: `https://lyceum.nstu.ru/rasp/schedule.html`.[file:79]
- На странице подключается скрипт вида `nika_data_YYYYMMDD_HHMMSS.js` через `<script src="nika_data_*.js">`.
- В файле содержится глобальная переменная:

```js
var NIKA = { /* JSON-подобный объект */ }
```

### 3.2. Основные узлы объекта NIKA

NIKA содержит как минимум:

- `CLASSES`: словарь `class_id → строковое имя класса` (например, "5а", "10-3").[file:79]
- `TEACHERS`: словарь `teacher_id → ФИО учителя`.[file:79]
- `ROOMS`: словарь `room_id → название кабинета`.[file:79]
- `SUBJECTS`: словарь `subject_id → название предмета`.[file:79]
- `CLASSGROUPS`: словарь `group_id → название группы` ("Группа 1", "Девочки", "Мальчики" и т.п.).[file:79]
- `LESSON_TIMES`: массивы таймингов уроков:

```json
"LESSON_TIMES": {
  "1": ["8:15","9:00"],
  "2": ["9:10","9:55"],
  ...
}
```

- `PERIODS`: учебные периоды с датами `b` (begin) и `e` (end).
- `CLASS_SCHEDULE`: расписание по классам.
- `TEACH_SCHEDULE`: расписание по учителям.[file:79]
- `CLASS_EXCHANGE`: замены по классам.
- `TEACH_EXCHANGE`: замены по учителям.

### 3.3. Структура CLASS_SCHEDULE и TEACH_SCHEDULE

`CLASS_SCHEDULE`:

```json
CLASS_SCHEDULE: {
  "period_id": {
    "class_id": {
      "daylesson_key": {
        "s": ["subject_id", ...],
        "t": ["teacher_id", ...],
        "r": ["room_id", ...],
        "g": ["group_id", ...]
      }
    }
  }
}
```

`TEACH_SCHEDULE`:

```json
TEACH_SCHEDULE: {
  "period_id": {
    "teacher_id": {
      "daylesson_key": {
        "s": ["subject_id", ...],
        "c": ["class_id", ...],
        "g": ["group_id", ...],
        "r": ["room_id", ...]
      }
    }
  }
}
```

- `daylesson_key` — строка вида `"107"` (первый символ — день недели 1–6/7, остальные — номер урока).[file:79]
- Массивы `s/t/r/g` и `c/g/r` могут содержать несколько значений (многогрупповые слоты).

### 3.4. Алгоритм парсинга и нормализации

Модуль `ScheduleFetcher`:

- Загружает `schedule.html`, извлекает `src` для `nika_data_*.js`.
- Загружает JS-файл с учётом User-Agent и, при необходимости, HTTP/HTTPS-прокси (из `Config`, особенно при деплое в РФ).[file:79]
- Находит фрагмент `var NIKA = {...};`, извлекает тело объекта:
  - балансирует фигурные скобки;
  - обрезает префикс `var NIKA=` и суффикс `;`.
- Пытается десериализовать через `json.loads`; при ошибке логирует и, по согласованию, использует JS→JSON‑парсер.
- Сохраняет полный текст JS в таблицу `raw_nika_cache` для краткосрочного дебага.

Модуль `NikaNormalizer`:

- В методе `build_metadata()` строит доменные модели `Class`, `Teacher`, `Room`, `Subject`, `Period`.
- В методе `build_class_lessons()` разворачивает `CLASS_SCHEDULE` и `CLASS_EXCHANGE` в список `LessonInstance` по классам.[file:79]
- В методе `build_teacher_lessons()` разворачивает `TEACH_SCHEDULE` и `TEACH_EXCHANGE` в список `LessonInstance` по учителям.[file:79]
- Для каждого слота:
  - определяет дату по `PERIODS` и дню недели;
  - применяет замену из `CLASS_EXCHANGE`/`TEACH_EXCHANGE`, если есть;
  - при `s == "F"` или пустом предмете помечает урок как отменённый (`is_cancelled = True`) и не пытается искать учителей/кабинеты;
  - использует `.get("t", [])`, `.get("r", [])`, `.get("g", [])` для безопасного доступа к массивам в заменах (`{"s":"F"}` может не содержать `t/r/g`).[file:79][file:27]
